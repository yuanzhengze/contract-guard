# 真实模型评测报告（v0.1）

- 模型：`glm/glm-5.3`（OpenAI 兼容代理）
- 命令：`npm run eval -- 3`；`npm run e2e`
- 样本：`samples/sample-contract.pdf`（软件开发服务合同，16 个条款，约 2000 字，**预埋 8 处对乙方不利的风险**）；`samples/fair-contract.pdf`（条款对等的咨询协议，用于反向测试误报）

## 1. 召回与可溯源（3 次独立运行）

| 运行 | 召回 | 引用可定位率 | 风险数（高/中/低） | 安全评分 | 耗时 |
|---|---|---|---|---|---|
| #1 | **8/8** | 100% | 11（7/3/1） | 25 | 67.9s |
| #2 | **8/8** | 100% | 10（7/2/1） | 27 | 67.7s |
| #3 | **8/8** | 100% | 10（7/2/1） | 27 | 63.8s |

改造 LLM 客户端（见 §4 #6）后回归 2 次：8/8、8/8，可定位率 100%，耗时 70.0s / 73.7s。

目标：召回 ≥ 7/8、可定位率 ≥ 90% → **5 次运行全部通过**。
预埋项以外，模型还稳定发现了 **“开票与付款绑定、甲方无责”**（第 4.4 条）—— 这是写合同时无意留下的真实风险，说明模型不是在“背答案”。

## 2. 反向测试（误报）

条款对等的咨询协议：两次评分 **91 / 89**，高风险均为 0，仅有中 1（尾款确认条件模糊）、低 1–2（双方均可任意解除等）。
结论：模型能区分“对等”与“不公平”条款，**没有为了显得有用而夸大风险**。

## 3. 前端端到端（真实模型，jsdom）

20 项全部通过：审查约 65s、23 种进度文案（含真实的“已发现 N 处风险”）；卡片 ↔ 原文双向定位；等级筛选；复制建议；“追问这条”带上下文；流式输出 31 次增量；参考条款可点回原文；停止生成；导出报告（含免责声明）；埋点漏斗正确。

## 4. 过程中发现并修复的问题（AI Native 迭代记录）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 首测引用可定位率 90%（1 条失败） | 模型把同一条款中不相邻的两句拼成一句引用 | 定位算法增加“按标点拆段 → 分段定位 → 覆盖率 ≥60% 且距离近则取覆盖区间”，展示的永远是真实原文 |
| 2 | 示例合同得 **0 分** | 线性扣分（−15/高），7 个高风险即归零，所有差合同失去区分度 | 改为乘法递减（每个高风险扣当前分 15%），同一合同得 25 分 |
| 3 | “尾款什么时候付”检索到前言 | 用户口语与合同用语不一致（尾款 vs 剩余款项） | BM25 前加口语 → 合同用语的查询扩展表 |
| 4 | 评测偶发 `fetch failed` | 代理网络抖动 | LLM 客户端加入指数退避重试（网络 / 限流 / 5xx / 超时），取消与鉴权失败不重试 |
| 5 | 参考条款 chips 漏掉 “第4.3条” 形式的引用 | 模型用阿拉伯数字子条款号，条款编号为中文 | 前端识别「第四条 / 第4条 / 第4.3条 / 按4.3」 |
| 6 | 端到端回归时审查**卡死 180 秒**才超时 | 非流式请求下，代理偶发“连接已建立但迟迟不返回”，只能等总超时 | LLM 客户端统一改为 SSE 流式：用**空闲超时**（45 秒无任何字节，含推理过程）判定卡死并自动重试；顺便把真实进展透传给前端——进度条显示“已发现 6 处风险…”，而不是假动画 |
| 7 | 用户刷新页面会中断审查、重复扣费 | 审查任务绑定在 HTTP 连接上 | 审查任务与连接解耦，结果写入会话，重连直接拿结果 |

## 5. 已知局限
- 单份合同审查约 60 秒（推理模型全文审查）；路线图：按类别并行审查 + 流式出卡片，首卡 < 15 秒
- 样本量小（2 份合同），召回率仅代表示例合同；路线图：建立 30+ 份多类型合同的评测集
- 审查立场固定为乙方
